# Phase 31 — Site Navigation Graph

> Passively build a navigation graph of every internal site as users browse. Store it as a YAML file in S3, render it as an interactive node graph in the dashboard, and inject it into agent prompts so agents navigate like power users.

## Why

1. **Agents navigate blind**: The agent gets a flat list of "Other Indexed Pages" — no topology, no relationships, no understanding of what connects to what. It wastes actions exploring when it could follow known paths.
2. **Users can't see what the agent knows**: The Sites page is a flat list of pages with element counts. No visual map. No sense of coverage. No way to see "my agent has explored 80% of this app."
3. **Dynamic routes are opaque**: `/invoices/inv_abc123` and `/invoices/inv_def456` are the same page shape, but the current `urlPattern` normalization is naive (only strips `/\d+/` and UUIDs). Slug routes, date routes, and nested dynamic segments aren't handled.
## What Ships

### 31b. Smart Route Pattern Detection

Replace the naive `urlPattern` normalization with a proper pattern detector.

**Current** (indexer.ts):

```typescript
// Only handles /123 and /uuid
.replace(/\/\d+/g, ':id')
.replace(/\/[a-f0-9-]{36}/g, ':id')
```

**New** — `apps/api/src/utils/url-patterns.ts`:

```typescript
export function normalizeUrlPattern(pathname: string): string {
  return pathname
    .split('/')
    .map(segment => {
      if (!segment) return segment;
      // UUIDs: abc12345-def6-7890-abcd-ef1234567890
      if (
        /^[a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{12}$/i.test(
          segment,
        )
      )
        return ':id';
      // Numeric IDs: 123, 42
      if (/^\d+$/.test(segment)) return ':id';
      // Prefixed IDs: inv_abc123, usr_xyz, cus_12345
      if (/^[a-z]{2,5}_[a-zA-Z0-9]+$/.test(segment)) return ':id';
      // Short hashes: a1b2c3d4 (8+ hex chars)
      if (/^[a-f0-9]{8,}$/i.test(segment)) return ':id';
      // NanoIDs / CUIDs: V1StGXR8_Z5jdHi6B-myT (20+ alphanum with mixed case)
      if (
        /^[a-zA-Z0-9_-]{20,}$/.test(segment) &&
        /[a-z]/.test(segment) &&
        /[A-Z]/.test(segment)
      )
        return ':id';
      // Date segments: 2026, 2026-03, 2026-03-27
      if (/^\d{4}(-\d{2}){0,2}$/.test(segment)) return ':date';
      // Slugs that look dynamic (contain numbers mixed with letters): my-post-123
      // Keep these as-is — they might be real routes like /blog/my-post-123
      return segment;
    })
    .join('/');
}
```

Both extension (client-side pattern for indexer) and backend (authoritative normalization + merge) use the same logic. Shared via `packages/shared/src/url-patterns.ts`.

### 31c. Graph Builder — Deterministic Merge Logic

**New file**: `apps/api/src/storage/sitemap.ts`

Core logic:

```typescript
interface SitemapNode {
  title: string;
  type: string;
  description: string; // generated by fast model on first discovery
  elements: number;
  visits: number;
  lastVisited: string;
  examples: string[]; // up to 5 real URLs that matched this pattern
  discoveredAt: string;
}

interface SitemapEdge {
  from: string; // urlPattern
  to: string; // urlPattern
  label: string; // link text
  type: 'nav_link' | 'breadcrumb' | 'redirect' | 'form_submit';
  traversals: number;
}

interface Sitemap {
  domain: string;
  version: number;
  lastUpdated: string;
  stats: {
    totalNodes: number;
    totalEdges: number;
    totalVisits: number;
    coverageScore: number;
  };
  nodes: Record<string, SitemapNode>;
  edges: SitemapEdge[];
}
```

**Update flow** (called from `POST /api/sites/:domain/pages`):

```
1. Download existing SITEMAP.yaml (or create empty)
2. Parse with js-yaml
3. Upsert node by urlPattern:
   - New node? → create with visits=1, generate description via fast model (fire-and-forget)
   - Existing? → visits++, update lastVisited, update elements count, merge example URLs (cap 5)
   - NEVER overwrite title/description with new data — keep the best version
4. Upsert edges from navigationLinks:
   - Normalize each link.href to urlPattern
   - Match by (from, to) key
   - New edge? → create with traversals=0
   - Existing? → update label if better (longer, more descriptive)
5. Recompute stats
6. Upload updated SITEMAP.yaml
```

**No-op optimization**: If the node already exists AND no new edges are found AND no new example URLs → skip the write entirely. This eliminates redundant S3 writes on repeat visits.

### 31d. Node Descriptions — Fast Model, Once

When a new `urlPattern` is discovered (first visit), fire a fast model call:

```
Given this page:
- URL pattern: /invoices/:id
- Page title: "Invoice #12345 - Acme Corp"
- Page type: detail
- Elements: 18 (3 buttons, 2 tables, 4 links, 1 form, 8 inputs)
- Navigation links: ["Back to Invoices", "Edit Invoice", "Download PDF"]

Write a 1-sentence description of this page's purpose and key capabilities.
```

→ `"Single invoice view with line items table, payment history, and status change actions (approve/reject/void)"`

This is **fire-and-forget** — the node is created immediately with `description: ""`, and the description fills in asynchronously. If the model call fails, the node still exists.

The agent can update descriptions via `save_knowledge` (targeting SITEMAP.yaml via a new `update_sitemap_description` internal tool or a structured mode).

### 31e. Agent Prompt Integration — Tree View

Replace the flat "Other Indexed Pages" section in `prompts.ts` with a tree-formatted site graph.

**Before** (flat list):

```
## Other Indexed Pages
- /dashboard (Dashboard, 12 elements)
- /invoices (Table, 45 elements)
- /invoices/:id (Detail, 18 elements)
- /settings (Settings, 8 elements)
```

**After** (topology-aware tree):

```
## Site Navigation Graph (app.example.com)
12 pages mapped, 18 navigation paths, 347 total visits

/dashboard — Main Dashboard (dashboard, 12 elements)
  → /invoices — "Invoices" nav link (52 traversals)
  → /reports — "Reports" nav link (23 traversals)
  → /settings — "Settings" nav link (15 traversals)
/invoices — Paginated invoice list with filters and CSV export (table, 45 elements)
  → /invoices/:id — "row click" (47 traversals)
/invoices/:id — Single invoice view with line items and status actions (detail, 18 elements)
  → /invoices/:id/edit — "Edit" button (12 traversals)
  → /invoices — "Back to list" breadcrumb (38 traversals)
/settings — Account settings (settings, 8 elements)
  → /settings/billing — "Billing" tab (10 traversals)
  → /settings/team — "Team" tab (8 traversals)
```

Agent can now say _"I know /invoices links to /invoices/:id via row click — I'll navigate there and click a row"_ instead of guessing.

**Token budget**: Tree view is capped at 80 lines. Sites with >80 nodes get pruned by `lastVisited` (keep the most recently visited). Full graph always available via `read_knowledge('domain', domain, 'SITEMAP.yaml')`.

### 31g. Dashboard — Interactive Graph Visualization

**Library**: `reactflow` (MIT, well-maintained, React-native, handles large graphs)

**New page**: `apps/web/app/(dashboard)/sites/[domain]/graph/page.tsx`

**Features**:

- Nodes positioned via dagre layout (top-to-bottom or left-to-right)
- Node appearance:
  - Color by `pageType` (dashboard=blue, table=green, form=orange, detail=purple, settings=gray)
  - Size scaled by `visits` (more visits = bigger node)
  - Opacity reflects recency (recently visited = full opacity, stale = faded)
  - Badge showing element count
- Edge appearance:
  - Thickness by `traversals`
  - Arrow direction shows navigation flow
  - Label on hover (link text)
- Interactions:
  - Click node → side panel with full details (description, elements, example URLs, last visited)
  - Hover node → highlight all connected edges
  - Search/filter bar to find nodes by title or pattern
  - Zoom to fit, minimap
- Coverage indicator: "72% of pages have descriptions" with progress bar
- "Pages without descriptions" filter to find gaps

**Entry point**: Sites list page gets a "View Graph" button per site that links to `/sites/{domain}/graph`.

### 31h. TanStack Query Hook

**New file**: `apps/web/lib/queries/use-site-graph.ts`

export function useSiteGraph(domain: string) {
  return useQuery({
    queryKey: ['site-graph', domain],

## Edge Cases

- **First visit to a domain**: Empty SITEMAP.yaml created, single root node, no edges
- **SPA navigation**: Extension fires `indexPage` on URL change (already handled), backend merges
- **Hash routes** (`#/invoices`): Strip hash, treat as pathname — some SPAs use hash routing
- **Query params** (`?page=2&sort=date`): Strip entirely for node identity, but note in metadata
- **Subdomains** (`app.example.com` vs `api.example.com`): Separate sitemaps per hostname (existing behavior)
- **Very large apps** (500+ routes): YAML stays manageable (500 nodes ≈ 25KB). Tree view in prompt capped at 80 lines. Dashboard uses virtual rendering.
- **Conflicting patterns** (`/users/admin` static vs `/users/:id` dynamic): Static routes take priority — if we see the same URL always resolve to "admin" title, keep it as `/users/admin` not `/users/:id`

## What This Does NOT Ship

- Version history or shadow copies — the AI handles file writes, trust it
- Agent-driven graph editing beyond descriptions — agent reads the graph, code builds it
- Cross-domain navigation tracking (site A links to site B)
- Automated crawling / spidering — graph builds passively from user browsing only
- Graph diffing UI in dashboard ("what changed since last week")
